Microsoft's agent-framework package was poisoned on PyPI for 45 minutes with a stealer that ran at every Python start-up. Two versions, one webhook, at most 50 victims, and a checklist for this morning

The attack did not need you to import the package. A .pth file in site-packages ran the stealer whenever any Python interpreter launched, which is why the window matters more than the download count.

Why it matters
SecurityScope by version (1.26.1, 1.26.2) and by time (20:35–21:30 UTC, Nov 17), then by artefact (the two .pth filenames, the _AF_TEL=1 marker, the webhook.site URL in egress logs). Rotate on any hit; audit managed-identity sign-ins for 24 hours after.
DevelopersPin agent-framework to 1.26.0 and add a check for .pth files appearing in site-packages to your container build. Install-time code is the attack surface, not import-time.
ExecutivesSecond poisoned Microsoft package on PyPI this year. Ask your platform team how long a bad version of a vendor framework would sit in your base images before anyone noticed.

At 20:35 UTC on Monday a version 1.26.1 of agent-framework, the Python meta-package that installs Microsoft Agent Framework, appeared on PyPI. A second version, 1.26.2, followed at about 21:08. Both were removed by roughly 21:30. Wiz, whose researchers published the full analysis, puts the package at around 41,000 downloads a week, and PyPI's own metadata at roughly 190,000 a month. Microsoft acknowledged the incident in a GitHub discussion and said it is investigating. The last clean version is 1.26.0, from November 12.

How it worked

The malicious wheels kept all the legitimate code. What they added was a .pth file in site-packages, named agent_framework_meta.pth in the first version and af_runtime_diag.pth alongside an af_runtime_diag.py in the second. Python executes .pth files when the interpreter starts, before any user code runs, so the stealer fired every time any Python process launched on the machine, whether or not the agent framework was ever imported. That is the detail that makes the exposure window the right unit of measurement rather than the number of people who used the package.

The payload read environment variables matching TOKEN, SECRET, KEY, AZURE, AWS, GITHUB and NPM; walked up to 300 entries in /proc to harvest other processes' environments; collected sixty to eighty credential files including Azure CLI state, .npmrc, pip.conf, .netrc, .git-credentials, Docker configuration, Hugging Face tokens and Azure DevOps agent files; requested Azure managed-identity tokens and instance metadata; and, in the second version, GitHub Actions OIDC tokens. Everything went out as one zlib-compressed, base64-encoded JSON blob in a single HTTPS POST to a hard-coded webhook.site address. Wiz notes the webhook was a free-tier endpoint capped at 100 requests, which bounds the number of victims whose data was accepted at about 50; a 200 response in your proxy logs means you were one of them.

Why it points to the pipeline

Only wheels were published, with no source distribution and no matching release of agent-framework-core, and nothing malicious appears in Microsoft's GitHub repository. Researchers at SafeDep flagged a PyPI maintainer account created the same day with rights to the package and five related projects; Microsoft has not confirmed that. The pattern is consistent with someone building and uploading outside the normal release process rather than with a compromised source tree. It is the second poisoned Microsoft package on PyPI this year after the durabletask incident in May, which was attributed to a different group; nobody has linked the two.

The counter-argument

The blast radius was small: 45 minutes, a webhook that stopped accepting data after 100 posts, and a package that most production systems pin by version. Pinning and lockfiles worked exactly as intended for anyone who used them. The reason the story matters anyway is that agent frameworks run with the broadest credentials in the building by design, on the same hosts developers use to log in to everything else, and a .pth-based stealer defeats the assumption that unused dependencies are inert.

What to do

Search lockfiles, container images and CI logs for agent-framework 1.26.1 or 1.26.2. On any host that installed them, look for the two .pth filenames in site-packages and for an _AF_TEL=1 environment marker. Grep proxy and DNS logs for webhook.site and the specific path Wiz lists. On a hit, rotate every secret the host could reach, treat OIDC tokens from workflows with id-token: write as exposed, and review Azure managed-identity and federated-credential sign-ins for the following 24 hours, which is how long a stolen token can remain valid. Going forward, flag .pth file creation during installs, build agent runtimes with an identity separate from the developer's, and remember that the vendor's publishing pipeline is now part of your supply chain.
