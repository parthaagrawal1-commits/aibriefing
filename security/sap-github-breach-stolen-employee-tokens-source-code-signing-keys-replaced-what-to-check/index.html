DevelopingSAP's GitHub breach: stolen employee tokens, altered source code, replaced signing keys, and the five checks every SAP customer should run this week

SAP says no customer business data was accessed; the reported mechanism, authentication tokens replayed against GitHub, is the one most enterprises are least prepared to detect, and the possibility of AI-assisted tooling is unconfirmed but plausible.

Why it matters
SecurityEnumerate every GitHub token with write access to repos you build from, kill the classic long-lived ones, and alert on clones of more than a handful of repositories by one identity in an hour.
ExecutivesAsk SAP for a written statement on which builds were signed before the key rotation and whether any delivered package was built from a touched repository.
DevelopersRequire signed commits on protected branches and verify signatures in CI. A modified commit that nobody signed should fail the build, not merge quietly.

SAP confirmed on Thursday that it is investigating a cybersecurity incident affecting its development infrastructure. The company's statement to SecurityWeek was short: it detected suspicious activity, took steps to protect customers and secure its services, and has so far found no evidence of unauthorised access to customer business data. It did not describe the attack.

The detail comes from German press. Der Spiegel, which broke the story citing SAP insiders and an internal staff notice, reported that the attackers obtained authentication tokens belonging to SAP employees and used them to copy and modify source code held on GitHub. DPA said it had seen internal communications placing the suspicious activity inside GitHub. Handelsblatt reported the response: signing keys replaced, GitHub access restricted, and automated development operations suspended across many teams. Cybersecurity News, citing the same reporting, said the investigation is being run under an internal name, Project Granite, and that an internal memo described the incident as active. Sources inside the company reportedly suggested AI agents may have been involved; SAP has not confirmed that and nothing published explains what role, if any, AI played.

Two things are not known. Whether any altered code reached a build that shipped to customers: no report says it did, and the signing-key rotation is what you would do to make sure it cannot. And whether the copied code was proprietary: SAP publishes a great deal of open-source and sample code on GitHub, and the reports do not name repositories or say whether they were public or private. SecurityWeek also notes that a ransomware group listed SAP on its leak site in late October, pointing to Latin American operations; it sees no connection between the two.

Why tokens, not exploits, are the story

Nothing reported suggests a vulnerability in GitHub or in SAP's perimeter. The mechanism, if Der Spiegel's sourcing holds, is credential replay: a token that already had permission to read and write repositories was used by someone who was not its owner. That is the same shape as the Mini Shai-Hulud npm campaign that hit SAP's own developer packages in May, which stole developer credentials through a poisoned package, and the same shape as most of the agent-assisted intrusions documented this month, from ARTEX to the Swiss cases. Machine-speed credential use is what AI tooling adds; it does not need new vulnerabilities.

SAP is also the company that, two days earlier, was reported to be weighing 10,000 job cuts in an AI-driven restructuring. Fewer engineers and more automated development operations is the direction every large software vendor is taking, and the attack surface it creates is exactly a pool of long-lived automation tokens.

What to do

  1. Inventory tokens. List every GitHub personal access token, deploy key and app installation with write access to repositories your builds consume. Classic tokens with no expiry are the target class; replace them with fine-grained tokens tied to SSO and a 30-day lifetime.
  2. Alert on bulk reads. A single identity cloning dozens of repositories in an hour is the signal here. Most organisations log it and nobody reads the log.
  3. Sign commits and verify in CI. Require signed commits on protected branches and make the pipeline reject unsigned ones. Modification of history by a valid token is the failure mode; signing makes it visible.
  4. Rotate code-signing keys on a schedule. SAP rotated after the fact. If your keys have not changed in a year, the incident that forces it will be worse than the maintenance.
  5. Ask SAP in writing. Which repositories, which window, which builds were signed with the old keys, and whether any delivered artefact was rebuilt. Pin any SAP open-source dependency you consume from GitHub to a commit you have reviewed until the answers arrive.

SAP has said it will not comment beyond its statement. Expect a customer notification once the investigation closes; until then the absence of evidence of customer-data access is a statement about what has been found so far, not a conclusion.
